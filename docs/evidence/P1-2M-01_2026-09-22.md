# P1-2M-01 — Near-Occurrence Miss / Cold-Recovery Boundary Case

## Classification
PROMPT_VERSION=P0R (P1 single-final-write scheduler path)
PRIMARY_VARIABLE=lead time (+2m)
WRITES_PER_WAKE=1
EVIDENCE_ROLE=ADVERSE_BOUNDARY_CASE
SCOPE=tested relay/runtime only

## Observed facts
INTENDED_DUE=2026-09-22 12:32:00 KST
OBSERVED_RECOVERY_INVOCATION=2026-09-22 13:34:56 KST (automation run context)
WRITE_OK=YES — prior final scheduler update accepted.
STATE_OK=YES — recovered run retained recurring RRULE and enabled state.
WAKE_OK_NEAR=NO — no substantive turn was observed around the intended 12:32 occurrence before hourly recurrence.
WORK_OK_RECOVERY=YES — recovered recurrence restored canonical GitHub research state and resumed substantive work.
DUPLICATE_EXECUTION=NO observed.
RECOVERY=PASS via preserved hourly RRULE.
RESULT=MISSED_NEAR_OCCURRENCE + RECOVERY_PASS

## What this evidence supports
1. A successful schedule write does not prove the intended near wake will be delivered.
2. Under this observed failure, preserved hourly recurrence provided cold recovery without creating a new automation.
3. +2m cannot be treated as a uniformly reliable fast-continuation default from the available sample set.
4. Recovery correctness and recovery latency are separate: this sample supports eventual cold resume, not a tight latency SLA.

## What this evidence does NOT support
- It does not prove every +2m occurrence fails; later +2m evidence was mixed.
- It does not prove +3m is universally safe; +3m is only the better tested practical default in this runtime.
- It does not establish an exact dispatch-delay distribution because runtime timing observations include early/late anomalies.
- It does not prove hourly recurrence is exactly-once; only no duplicate substantive execution was observed in this case.

## Counterfactual value
If recurrence had been removed when the near occurrence was missed, no tested cold continuation path would have remained. Therefore this case is direct adverse evidence for preserving recurrence while using a close-relative DTSTART.

If a provisional scheduler pre-arm had also been written, this case alone would not show that the extra write caused recovery: preserved hourly recurrence already explains the observed resume. Therefore the case does not justify an extra normal-path scheduler mutation.

## Falsification / supersession tests
This case should lose operational weight if either condition is reproduced under controlled comparable runs:
1. a lower lead class (including +2m) achieves repeated near-wake reliability equivalent to the promoted +3m class while recurrence and control policy remain unchanged; or
2. a simpler recovery mechanism removes recurrence yet demonstrates equal-or-better recovery reliability and latency without adding control cost.

A single later +2m success does not erase this adverse sample; the relevant evidence is the repeated distribution under controlled conditions.

## Reuse contract
Use this case when evaluating lower lead-time candidates, proposals to remove recurrence, claims that WRITE_OK implies WAKE_OK, or recovery designs that add scheduler writes. Cite the observed facts separately from the bounded inference; do not turn this one miss into a universal scheduler law.
